# ADR-0005 · 聊天优先交互模型:飞书机器人是人的界面,动作按性质分家

- 状态:已接受(2026-07-13,顺手 loop 定调)
- 相关:ADR-0004、`orchestrator/cockpit.py`、`orchestrator/publish.py`、`scripts/today.py`

## 背景
系统上线后跟服务器 agent 连,**暴露给人的界面是飞书机器人聊天**(不是 base)。人只管头尾,得能"在聊天里顺畅解决",base 作兜底/可视可调。要定清:哪些动作放卡片、哪些放聊天、哪些引导 base——不然要么啥都塞卡片(复杂脆),要么啥都甩 base(不丝滑)。

## 决策:动作按性质分家

| 动作 | 放哪 | 理由 |
|---|---|---|
| **批准 / 暂缓 / 勾 AI 声明** | **卡片按钮**(点一下,回调) | 高频、纯决定,一点到位不切换 = 丝滑最该花在这 |
| **回填发布链接** | **聊天里发链接,agent 认领**(base 兜底) | 刚发完小红书链接在剪贴板,聊天发一句"发了 &lt;链接&gt;"最顺;卡片输入框低频又要额外组件+校验,不划算 |
| **看今日/要拍/待发** | **卡片面板**(推私聊,上线推工作群) | `cockpit.today_panel` 聚合,一条消息看完 |
| 疑难 / 要改字段 | **卡片深链 → base** | base 是兜底,不追求全聊天 |

**红线不变**:人点按钮 = 人审(机器绝不自审、绝不自动发布);认领链接绝不瞎猜(多条命中返候选让人指定)。

## 实现(动作函数=服务器就绪的缝)
按钮/聊天背后的逻辑收口成**纯动作函数**,服务器 agent 的 webhook 只把"卡片点击/聊天消息"接到它们,不重写:
- `publish.approve(note_id, write)` — 草稿待发→已批准(人点=人审)。
- `publish.fill_publish_link(note_key, url, write)` — 按 record_id/标题/账号片段匹配**唯一**待发/已发缺链接笔记→写发布链接+标已发;**多条/零条→返候选,不落库**。
- 投递:`alerts.send`(hermes)推飞书;**当前发 bot 私聊**(p2p),上线再指向工作群(要群 chat_id + 确认,对外动作)。
- 卡片按钮回调 + 聊天认领的 webhook = **服务器 agent 的活**(没服务器跑不了);动作函数已就绪,接手直接接线。

## 后果
- 顺手验收(`verify_usable §⑦`)守"一条命令/消息看完今日";动作函数有单测锁(approve 只从草稿待发、fill 多条命中返候选)。
- 卡片输入框**刻意不做**(除非聊天认领被证明不够用)——避免为低频动作背复杂 UI。
- 交互模型记死,未来别再纠结"这动作放哪"。
