# P2 设计判断（实测证据 → P4 设计输入）

日期：2026-07-08。全部结论有实测或官方文档依据，非推断。

## 1. 自动化 workflow：API 只读，建创走 UI

- 实测：`GET /open-apis/bitable/v1/apps/{test}/workflows` → `code:0, workflows:[]`（接口可用）；公开 API 无创建 workflow 端点（仅 list/update status）。
- 实测：Base 复制 **不带自动化**（测试副本 workflows 为空）。
- 结论：自动化 = UI 一次性配置（见 P2_手动配置清单.md），且**不作为机器间事件通道**，只用于"通知人"。
- 推进器可用 `GET workflows` 做巡检探针（自动化被人误删时告警）。

## 2. 事件入口：heartbeat 轮询为主，webhook 不引入

- 约束：本地工作机无公网 IP，飞书自动化"发送 HTTP 请求"打不进来。
- 备选评估：
  - **heartbeat 轮询（选定）**：推进器每 N 分钟按视图/filter 读关键状态（`已批准`、`待发布` 等），单 writer 串行天然兼容、零新依赖、延迟分钟级完全够用（内容排产不是秒级业务）。
  - 飞书事件长连接（WebSocket）：SDK 支持，但 Bitable 自动化不能定向触发 bot 事件，改造收益低。
  - cloudflared/frp 隧道：引入公网暴露面与新运维负担，与"薄推进器"原则冲突。暂不引入；若未来要秒级响应再评估。
- 结论：**P4 的事件入口 = heartbeat 轮询关键状态 + cron 定时排产**，无 webhook 接收器。（PLAN §P4b 的"webhook 接收器"按此裁剪——roadmap 数据驱动修正 #1。）

## 3. 状态机语义（9 枚举定稿）

`想法储备→待拍素材→待出文案→草稿待发(=待审)→已批准→待发布→已发→已回流`，`暂缓归档` 旁路。
- 复用 `草稿待发` 承担"待审"语义（不加同义新状态，尊重既有 6 枚举与视图）。
- `已批准`（人审通过，推进器可组装发布包）→ `待发布`（发布包就绪+AI 声明已勾，等人发布）→ `已发`（人回填链接/日期）→ `已回流`（效果数据回填完成，推进器写）。
- 硬门：状态推进到 `待发布` 前，推进器校验 `AI声明=true`，否则拒绝并告警。
