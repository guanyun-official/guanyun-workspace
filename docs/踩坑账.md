## 一、核心病:「人想起来方便的逻辑,落实下来都是 bug」

在脑子里想通了,就当做完了。所有 bug 都是这一个形状。

| 想起来觉得方便的那句话 | 落实下来是什么 |
|---|---|
| "干跑嘛,不写库,提前 return 就行" | 干跑**跳过了整段去重** → 打印"今天派活 4 条",实跑**一条都不派**。而干跑是唯一能"先看看"的手段 —— **预览骗人一次,这个手段就废了** |
| "文件不在就返空串,稳" | 技能名错一个字 → **LLM 零技能、零 few-shot 裸写**。产出照样有,只是悄悄退化成通用口水文,**永不作声** |
| "复用在途稿,别新建重复" | 把**运营正等着审的稿**悄悄覆盖掉。他在卡片上看到 A,点进 base 变成了 B。("复用"对占位是对的,对已成稿的正解是**跳过**,不是覆盖) |
| "写个探针把 17 条链路都验了" | **没有任何人跑它**;手动一跑当场崩(`MaterialSource.SHOT` 这个属性根本不存在)。**一个验收器,自己是死码** |
| "加工失败就安全退回原图" | AI 判了该加封面、执行炸了(模型没开通),它**一声不吭**退回原图。人以为封面加上了 |
| "prompt 里写了篇幅硬要求" | LLM 写超了 8 个字,稿子照样落库,**锅甩给运营让他自己删** |
| "阈值可 env 覆盖,灵活" | **给红线装了个静音开关**:`GY_ACCOUNT_DAILY_PUB=999` → 今天已发 50 篇照样放行,**且不留任何痕迹** |
| "L16 加工环:验它默认是关的" | **一个功能靠"证明自己没开"通过了验收**。于是"17 条链路真跑"里,那一条是掺水的 |

**镜像(同样致命)**:**本可以直接做完的事,别想成要先造个东西。**
用户说"这批素材给 ootd 视频号" → 正确反应是**去 base 里把那批的『适用账号』写上**(一次操作,几秒)。
错误反应是"要不要给打标器加个自动规则/加个字段"。每多一个字段/开关,都是下一个死配置。

## 一·补二、**世界的形状不对,代码里就会长出钳制**(2026-07-14 用户点破)

素材表『类型』的 12 个值,**把"内容"和"形态"焊在一个字段里**:

```
上身图 / 上身视频   ← 同一内容的两种形态
面料·纹理特写       ← **只有"图"这一档**
细节图 / 空镜·场景  ← 也只有图
```

于是一条 **1.5 秒的面料特写视频,在这套词汇里没有地方放**。
而代码必须给它一个值,所以老 tagger 里长出了这条:

```python
if kind == "video":
    return raw if raw in _VIDEO_TYPES else "上身视频"   # 视频文件强制落视频类,默认上身视频
```

看图模型多半判对了(那就是个面料特写),**harness 把它的正确答案覆盖成了「上身视频」**。

后果一路滚下去:
- 库里唯一那条「上身视频」,真身是 **1.5 秒的糊布料特写**(我抽帧用自己的眼睛看的)
- board 报「ootd号 · 上身视频 · 已拍可用 **1** 条」—— **真实可用 0 条**
- 补拍单少催一条;**还有一条待审稿就是配着它出的**(真发出去 = 1.5 秒糊布料)

**这不是代码 bug,是世界缺了个位置。**
补位置(加『形态』字段,『类型』回归纯内容)之后,那条钳制**再也长不回来** —— 因为不需要了。

> **它卡住时,先问"世界里有没有它要的那个位置",再问"代码要不要加个规则"。**
> 加规则是最容易想到的,也几乎总是错的。

## 一·补、两个"静默"的坑(2026-07-14 真事故,都是**成功地做错了事**)

### 1. 飞书 select 的选项是**按 id 认的** —— 改选项会**清空所有单元格**

想给素材表『类型』加两个选项,于是 PUT 了一个**只带 name、不带 id** 的 options 列表:

```python
feishu_io._call("PUT", ".../fields/{fid}", data={
    "field_name": "类型", "type": 3,
    "property": {"options": [{"name": o} for o in 全部选项]}})   # ← 只有 name
```

飞书把**整组选项换掉**(发了新 id)→ **280 行的『类型』当场全空**。
API 返回 `code=0`,**成功**。没有任何报错。

- **改 select 选项 ≠ 追加选项。** 要保留就必须**把旧选项连它的 `id` 一起回传**。
- 救回来靠的是 `backups/test-2026MMDD/素材表.json`(每日全表备份)——**备份救了命**。
- 教训:**任何 schema 级操作,先备份、先在一行上试、再读回自证。** 它不会喊,它只会静静地把数据抹掉。

### 2. `install_skills.sh` 会把技能仓留在 **detached HEAD**

它按 `skills.lock.json` 的 sha `checkout` → HEAD 游离。
之后在技能仓里 commit,提交**落在游离的 HEAD 上**;`git push origin main` 推的是
**还停在旧 sha 的 main 分支** —— **静默无操作,退出码 0**。

于是"改完 push"这条纪律**在这种状态下无法执行,而且不报错**。
差点对外宣称"技能已推送" —— 是 `git ls-remote` 直接问 GitHub 才发现的。

> **纪律**:技能仓推完,必须 `git ls-remote origin refs/heads/main` 对一遍 sha,
> 且 `skills.lock.json` 的 sha **= GitHub 上的 main**(不是本地 HEAD,不是本地 origin/main 缓存)。
> 这条已进 `review_gate.sh`。

## 一·补三、**反向的谎:工具假装自己失败了**(2026-07-14 数字生命上班第一天抓到)

`alerts.send_card` 判成功是这么写的:

```python
ok = r.returncode == 0 and '"code":0' in (r.stdout or "")     # 子串匹配一个 JSON
```

而 `lark-cli im +messages-send` 真吐出来的是:

```json
{"ok": true, "identity": "bot", "data": {"chat_id": "...", "message_id": "om_..."}}
```

—— **根本没有 `code` 这个键**(那是 `lark-cli api` 的形态,**两个子命令形态完全不同**)。
于是 `send_card` **永远返回 False,而消息其实真的发出去了**。

它的 docstring 上一版写着:"发失败**如实返回 False** —— 绝不假装发出去了(人在等,而消息根本没到)"。
**它防的是"假装成功",结果掉进了反方向:假装失败。**

**假装失败更毒** —— 它诱导 agent 反复重发。数字生命信了它,重发、又发探针诊断,
**真人群里落了 4 张卡**。它自己发现后撤回了。

### 而我修它的时候,在同一个函数上又踩了两次

1. 我"想当然"改成判 `code == 0` —— **真跑一次才发现 im 子命令根本不返 code**。
2. 我在返回值里塞了两句"自证命令"提示:`im +messages-get` / `im +messages-delete`
   —— **这两个子命令根本不存在**(真名 `+messages-mget`;撤回得走 raw api)。
   **在一个刚修完"工具在骗人"的函数里,我又亲手塞了两句骗人的提示。**

> **「别信形态,先真读一遍 API 返回」—— 今天在同一个函数上栽了三次。**
> 推论:**命令名也别猜**,去 `--help` 里看。写进产物的每一句"你可以这样做",都得先自己跑一遍。

### 又一个"工具假装自己活着"的坑:代理劫持 localhost(2026-07-15)

起了引擎服务(`:9001`),`curl localhost:9001` 返回 200 "有人听" —— **假的**。
这台机器有全局代理(`http_proxy=127.0.0.1:10820`),而 `NO_PROXY` 里**没有 localhost**。
于是任何连本地服务的 client 都被代理劫持,拿到一个**不是引擎的响应**。

这和「一·补五」那个 Privoxy 坑是同一个,**而且我 2026-07-14 就记过一次**(见上表第一行),
2026-07-15 又差点栽。拦住的还是那一条:**别信"有人听",真读返回** ——
引擎的真响应带 `draft_id`/`success:true`(`curl --noproxy '*'` 或 `NO_PROXY` 含 localhost 才看得到)。

> 连本地服务:`export NO_PROXY="localhost,127.0.0.1,$NO_PROXY"`,否则代理替它说谎。
> (feishu_io 早就为飞书内置了 `LARK_CLI_NO_PROXY=1` —— 同一个病,不同的服务。)

## 二、别信形态,先真读一遍 API 返回

**同一个坑,栽过八次。**

1. **飞书 `search` 的 link 字段**:返回 `{'link_record_ids': [...]}`,**没有 text**;而 `list_records`/`get_record` 返回 `[{'record_ids': [...], 'text': '名'}]`。
   用 `bitable.text()` 读 search 结果 → **永远是空串** → 在途笔记永远找不到 → **每次出稿都新建一行** → 运营卡片上堆了 5 条同号同模式的重复稿。

2. **小红书 `note` 原子的正文**:在 `note.desc`,且**必须带 `xsec_token`**(feed 里给了 `xsecToken`)。
   我没带 token、又读了顶层 `desc` → 拿到空壳 → **对外宣称"非登录抓不到正文"**,据此改了红线设计去绕开它。
   **全错。** 带上 token 读 `note.desc`,正文就在那儿(真抓:186 字 / 311 字,赞 10万+)。

3. **ARK 的 404**:返回体里写着 `{"error":{"code":"ModelNotOpen","message":"…请在控制台开通…"}}`。
   老代码只留 `HTTPError: 404 Not Found` → 我差点断言成"端点写错了"。**报错不带真相 = 等于没报。**

4. **飞书 link 字段清空后**:是 `[{"table_id":"…","text_arr":[],"type":"text"}]` —— **壳非空、内容为空**。
   `bool(field)` 判它**永远是 True**。要用 `bitable.link_record_ids()`。

5. **`lark-cli` 把报错写在 stderr,成功才写 stdout**(2026-07-15,查笔记本发烫时撞出来)。
   `feishu_io._call` 只看 `r.stdout` → 出错时 stdout 是**空的** → `"{" in out` 为假
   → 落进重试分支 → **睡 1s·2s·4s·8s,重跑 5 次** → 抛「5 次重试未成功」。

   两条都在骗人:
   - **任何一个错都烧 36 秒 + 5 个进程**。而表 id 写错这种事,**重试 5 次还是错**。
   - **真话被扔了。** lark-cli 在 stderr 明明说了 `[1254041] TableIdNotFound`,
     数字生命收到的却是「重试未成功」—— **它不知道自己写错了,只会去重试,不会去改。**

   连带查出 `get_record` 的 `except FeishuIOError: return None` ——
   表 id 错、没权限、网络断,**全被吞成"这条记录不存在"**。
   真问飞书:记录不存在的真码是 **1254043**(格式非法/同长不存在/乱编,三种全回它)。
   **只有它 → None,其余一律抛。**

   > 修完真跑:错 → **1 秒 · 1 个进程 · 说真话**。
   > **报错不带真相 = 等于没报**(第 3 条已经这么写过一遍了,我又犯了)。

6. **飞书多选字段是 `["A", "B"]`,而 `bitable.text()` 会把它拼成 `"A,B"`**(2026-07-15)。
   于是「一张图两套衣服」在分桶时变成**第三套叫「A,B」的衣服** ——
   「浅蓝」真撞了 5 条稿,board 拆成 3 条 + 2 条,**读不出那个 5**。
   而这个数字**唯一的用途就是判撞衫**。→ 新增 `bitable.multi()`。
   连带:CLI 的 `_kv` 只产字符串 → 多选字段**根本写不进**(`MultiSelectFieldConvFail`)。
   数字生命原话:「**服务器上的 agent 只有 CLI,它改不了款式。**」

7. **网盘 `list_dir` 返回的是 `is_dir`,不是 `isdir`**(2026-07-15)。
   我用 `.get("isdir")` 判目录 → 恒为 None → 扫出来 **0 个文件**(真实 479 个)。
   **我是在写「别猜形态」这条教训的同一天猜错的。**

8. **飞书 url 字段是 `{"link": "https://…", "text": "显示名"}`,而 `bitable.text()` 是 text 优先**
   —— 对 url 字段**恰好把唯一有用的那半扔了**。

   后果在人面上:今日卡片给运营的素材行是 `🖼 ST-260702-004 → 2026-07-02 175621.heic`。
   **文件名。他点不开,也不知道在网盘哪个目录。** 而能开的分享链**一直躺在库里**。

   这个形态被**手写拆解过三处**(`materials` / `board` / `publish`),**其中一处拆错**。
   → 新增 `bitable.url()`,**形态只拆一遍**。三处统一走它。

→ 「已拍可用」改名「**已登记**可用」。**一个字用错,系统就去骗摄影师。数什么就叫什么。**

## 三、检查器自己得了它要抓的病(栽过**五**次)

**规矩:检查器必须过"把 bug 塞回去,看它报不报"这一关。** 否则它就是下一个空壳。

**第五次就在 2026-07-15,而且是被我自己的注释骗的。**
我把「落在 02-AI生成/ 强制 AI生成」这条法律从 `ingest.py` 归位到 `guard.py`,
顺手写了道门守它:`assertIn("guard.source_from_path", 源码文本)`。
然后把那行调用**整行删掉** —— **门照样绿**。
因为那个名字在**我写的注释**里也出现了(「已归位 guard.source_from_path」)。

**这一节白纸黑字就写着这个病(「加一句注释提到那个函数名 → 绿」),我一边写一边又犯了一遍。**
逮住它的**只有"把 bug 塞回去"这一步**。现在走 AST:**注释里写一万遍也没用,必须是一次真调用。**

1. **regex 数 `fn(`,注释里出现的名字也算调用点** → 「假承诺」检查当场变成摆设(把假承诺塞回卡片,它一声不吭)。
2. **改用 AST 后,helper 根本没插进文件**,而且没验证就往下走。
3. 于是它成了最恶劣的一种空壳:**平时永远是绿的,只在真该报警的那一刻炸掉**(循环体只在"真有问题"时才执行)。
4. **死码检查一直没换到 AST** —— 审查器里躺着两套数调用点的逻辑,一新一旧,而**旧的那套正是它自己 docstring 里骂过的**。
   结果:`vision.see()` 零调用却一直"绿"着(名字在注释里出现过两次)。

**误报比漏报更毒**(喊三次狼来了,门就没人看了)。同一轮里造出的两个假红:
- 钩子被当**值**引用(`return compose.ai_decide` —— 没有括号)→ 被判死码。而整个 ADR-0006 钩子架构就是靠传函数值实现的。
- `skills_lock.validate()` 在 **`check_p1.sh` 里被调用**,而 AST 只扫 `.py`,看不见 shell。

## 四、人面缺陷(机器查不到,只有真读才发现)

- **给错读者**:补拍单给摄影师的"参考",给的是 `skills/xxx/SKILL.md` 的**文件路径**。他在拍摄现场,怎么打开?
- **一帧当全部**:视频备注写着「浅粉色…**局部特写**…」,而那是**抽出来的一帧关键帧**。让摄影师"照着这个拍上身视频",他当场懵。(修法:备注前面标 `(视频关键帧)`。)
- **黑洞**:运营批了的稿被门拦住,不在任何视图里出现 → **他以为发出去了**。
- **零数据编结论**:周报只有 1 条、均赞 0.0,却写「本周最有效:视频唯美OOTD —— 可加权多产」。
- **建议没基于真实状态**:让运营"去回填链接",而那条稿的链接**他早就填了**。
- **把技术标识符甩给运营**:周报里出现 `GY_METRICS_MODE=real`。他不敲终端。
- **拦住却不说清楚**:门正确拦下了覆盖待审稿的操作,然后甩了一个 **Python 堆栈**。
- **死指针**:账号表 `workspace_ref` 全写着 `brands/观云/accounts/…` —— 改名后那个目录**根本不存在了**。没代码读它,但**人会点它**。

**"没代码读" ≠ "没人读"。人也是读者,而且是最容易被骗的那个。**

## 五、成本

`claude -p` **每次调用吞 ~33K token 的 CLI 系统提示**(实测:让它只回"测试成本"四个字,`cache_creation=32766`,花 1.48 元)。
一条 200 字小红书文案 2~3 元,**95% 的钱付给了系统提示**,与文案长短、模型档次几乎无关。
→ 切 ARK 直连(豆包):同样的稿约 0.0x 元,**便宜两个数量级**。
