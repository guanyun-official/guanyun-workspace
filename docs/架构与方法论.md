# 巧荷 Workspace · 架构与方法论（优化至 2026-07-08）

> 这份是权威说明，讲清"为什么这么设计"。工程细节见 `AGENTS.md`，阶段验收见 `docs/PLAN.md`。

## 一、道：一句话方法论

**从"人触发 AI 干活"升级为"AI 管整个内容 loop，人只挂 SKU + 审批（甚至连审批都可交给 loop）"。**

智能不在某个居中的大 agent，而在**结构**里：把内容生产全生命周期做成可读/可原子操作/可验证的数据基建，agent 才能逐格接管。Base 是运营事实与状态流的唯一源，workspace 是可版本化 know-how 的唯一源；不是两边各存一份再同步。agent 按状态领活，不是统管全局的大脑。

## 二、三层分离（本架构的骨）

这是全部设计的核心，也是"别一个模式加一个脚本"的答案：

| 层 | 是什么 | 变的粒度 | 落在哪 |
|---|---|---|---|
| **能力 = skill** | 可复用的"怎么做"（生成文案、拆解账号、摄入素材、剪视频） | 跨账号通用，几乎不变 | git 技能仓库（qiaohe-skill、video-engine），`skills.lock` 锁版安装 |
| **模式/画像 = data** | 每个账号的两张脸：**画像**(发什么/怎么写) + **strategy/playbooks**(怎么运营/每套方法论怎么产) | 每号一份，**改这里** | `brands/巧荷/accounts/{号}.md` |
| **引擎 = 泛化** | 通用解释器：读声明/状态 → 执行 | 零账号特定代码，永不动 | `orchestrator/draft.py`（薄执行器：读声明→取该号 gen_skill→加载 few-shot 组稿→过红线闸→写草稿待发；大刀阔斧后取代已删的重引擎/planner） |

**加新账号 / 加新模式 / 加新内容类型 = 改 data 或 Base tag，不改代码。硬编码 Base/表/账号/模式 = 原罪。**

### 唯一源边界（SourceOwnership）

详见 `docs/SOURCE_OWNERSHIP.md`。当前铁律：

- Base owner：账号注册表、小红书号/主页、上线与发布状态、排期、内容类型 tag/格式/所属账号、运行与效果数据。
- workspace owner：账号画像、strategy、playbooks、内容切面、标题/正文公式、素材需求、使用哪个生成 skill。
- skill owner：可复用“怎么做”的能力；账号/模式差异不做成 skill，放进 workspace playbook。
- 非 owner 只能存外键、索引、员工界面摘要或可重算快照；引擎不得消费非 owner 的 know-how 字段。

### 账号的两张脸（回答"模式和方法论是一个东西吗"）

同一个账号，两个 data 侧面，都不是 skill：
- **画像 `{号}.md`** = 内容方法论（发什么、什么调性、取哪类素材切面）→ 喂**生成**（薄执行器 `compose_prompt` 注入）。由 `account-teardown` 技能从该号已有内容总结填充，不手编。
- **strategy/playbooks frontmatter** = 运营模式（缓发节奏 cadence、自主度 autonomy、素材来源 sourcing）+ 每套方法论（content_type、material_needs、gen_skill）→ 喂**薄执行器生成**（取该号 playbook 的 gen_skill）。

skill 是产出/消费这两张脸的能力：account-teardown（产画像）、gen_skill（用画像+few-shot 生成）；薄执行器 `draft.py` 用 strategy 取该号 gen_skill。

## 三、六角色归位（谁干什么）

| 角色 | 承担者 | 铁律 |
|---|---|---|
| 账本（唯一真相源） | 飞书 Bitable（工作台 = 测试库 `ZhzJbf…`，生产库 `N9IVbi…` 焊死不碰） | 一条内容一行，状态列是唯一真值 |
| 大脑（能力） | git skills | 只装"怎么做"，实例配置外置注入 |
| 手（执行壳） | Claude Code 主力 / Codex 备用 | 易耗品，可换，`python3 -m scripts.draft_one` 谁触发都行 |
| 推进器（loop） | 大刀阔斧后=薄执行器 `orchestrator/draft.py`（按需/手动；内容 cron 待轻调度器见 #8） | 只到草稿待发，绝不自动发布 |
| 脸（员工界面） | 飞书原生：表单/看板/审批卡片 | 员工永不碰 agent |
| 人 | **挂 SKU/素材 + 审批**（或声明 full 连审批都免） | 两个人审硬门（内容审 + 发布勾 AI 声明）不可自动化 |

## 四、内容 loop 全生命周期（每天怎么转）

```
想法储备 → 待拍素材 → 待出文案 → 草稿待发(=待审) → 已批准 → 待发布 → 已发 → 已回流
                                        ↑人审卡点          ↑人发布勾AI声明   ↑效果回填
```

**大刀阔斧后 = 薄执行器按需推进**（重引擎/planner/heartbeat/route 已删）：
- **生成**：`python3 -m scripts.draft_one --account <号>` → 薄执行器读该号声明 → 取 playbook 的 gen_skill → 加载其 SKILL.md 真实帖 few-shot → 组稿 → 过 base 红线闸 → 写笔记表「草稿待发」。`--llm real` 真生成（预算帽硬限），stub 默认零成本。
- **人审两道门**（不可自动化，红线）：① 内容审（读草稿改稿）② 手机发布并**必勾 AI 声明**，回填链接。
- **硬闸**（焊代码里，薄执行器绕不过）：只写测试库（`guard.assert_base_allowed`）、AI 声明门、防搬运出口闸；薄执行器只到「草稿待发」，绝不代勾、绝不自动发布。
- **素材选择 / 效果回流**：素材接入（issue #32）、回流采集（`metrics` extract 原语，待接薄执行器）是大刀阔斧后的「加能力」阶段，加 skill 不改 schema。

## 五、素材：从乱到有序（agent 理解驱动）

原始素材乱拍、没命名、没挂钩 → `ingest`：scan（agent 多模态看懂每个文件）→ link（软链上墙，**原件不动**）→ register（挂 SKU + 命名 + 登记素材表）+ manifest（地址被登记=在空间中有）。
"在空间中有" = 物理存在或地址被登记；引用优先不搬运。素材放本地/云盘存链接，表不当媒体库。

## 六、可迁移性（为什么不会被绑死）

- 技能在独立 git 仓库，`skills.lock` 锁 SHA/tag，marketplace version 控版。
- 执行壳可换（Claude Code/Codex，AgentSkills 开放规范互认），换壳成本趋近零。
- 状态在表、能力在 git、模式在 data、资产在盘——没有一样绑死在某个壳或某个 agent 的记忆里。

## 七、人机分工（人唯一介入的两件事）

1. **挂 SKU/素材**（ingest 帮你，甚至 agent 看懂帮你挂）。
2. **审批**（内容审 = 飞书翻状态列；发布 = 手机发 + 勾 AI 声明）。声明 `autonomy:full` 可连审批都免，完全交 loop。

其余（排期、生成、催拍、提醒、回流）引擎按每号声明自己转。

## 八、这套架构能装下的模式（都是写声明，零代码）

**改声明即用(已实现)**：考据慢发 / 集中拍上身+缓发 / 实验号手动 / 品牌叙事低频(已设) / 爆款模仿(`sourcing:trend_imitate`) / A/B 测试(两套 strategy 轮换) / base 侧暂停某号(`自动排产`)。

**占位声明(写了但代码未消费,要接 workflow 代码才生效,见 ADR-0008,别当"零代码即用")**：AI 全自主(`autonomy:full`,**有意不实现**——违反人审红线)/ 节日爆发(`cadence.pattern:burst`、`posts_per_day` 多发,语义待定)/ 蹭热点插队优先级(`sourcing:trend_insert` 有 hint、插队排序未实现)。**架构"改声明零代码"的承诺只对上面"已实现"那档成立;占位档需接代码。**

## 九、workflow 关节 vs skill 叶子（确定性 vs 智能，放哪的判据）

> §二 分的是 know-how **落在哪**（能力/data/引擎）；这一节分的是**另一条正交轴**：一个步骤该写成**确定性代码**，还是交给**智能体/技能判断**。两条轴一起用，别混。

2026 行业共识（Anthropic《Building Effective Agents》《Agent Skills》+ 多方综述）：确定性工作流 vs 自主智能体**不是二选一，是 hybrid 谱系**。两句原则刻墙上：**"用能过验收的最简方案，只在必要时加复杂度"**；**"你拥有目标和护栏，不是每一个分支"**。

**判据（一句话记死）：要可靠/安全/可观测/可复现的 → 进 workflow（确定性代码，自己拥有）；要智能/品味/适应的 → 留技能（叶子）。** 流程不规定智能步骤的**内容**，只规定它的**位置、顺序、前后置状态、护栏**；技能在自己那一格全权。

落到本仓：

| workflow 关节（确定性，焊代码里） | skill 叶子（智能，交模型/技能） |
|---|---|
| 笔记状态机、`daily_dispatch` 节奏、`sourcing` 路由（Router pattern） | 写文案（gen_skill few-shot） |
| `select_materials` 谓词、`guard` 红线、provenance/AI声明（`processing.derive_source` + `guard.ai_declaration_required`） | 看图打标、爆款拆解、加工决策/执行 |
| `feishu_io`/`netpan`/`bitable`/`vision` 适配器 seam、`processing.maybe_process` gated 落点 | 周复盘读效果→提 SKILL.md 改进 PR |

**加工环（ADR-0006）是这条判据的活案例**：决策/执行=技能，落点/provenance/AI声明=代码焊死，整环默认关。

**为什么不上重框架（LangGraph/LangChain/CrewAI 等）：** 最佳实践就是"最简够用即可"；重框架的代价是抽象税 + 藏控制流 + 调试难 + 锁定，且业界自承"多技能编排框架至今不成熟"。越是 agent 驱动，越要"能力(技能)+ 安全护栏(自己的代码)"，而非一张预先画死的图。**轻 workspace = 自己拥有的右尺寸框架**；该投的是继续养 rails/seams（JIT 按需长），不预造。真到"多个长时并发 agent + 持久共享态 + 回放"同时出现，才考虑加一**薄**协调层，且只加需要那片。
